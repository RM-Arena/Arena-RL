# DeepSeek V4.1 Flash 全场对局验证

2026-10-18，真实的 `deepseek-flash` API 监督了三场相互独立的 2027 对局。每场对局中，一台学习得到的红方 W3（3 号槽位）对阵脚本控制的蓝方重型（型号 2711，1 号槽位）和 W3（3 号槽位）。对手配置分别为 siege、raid 和 hunt。这种非对称的 1 对 2 设置是一个已声明的评估场景，而不是标准的全阵容锦标赛，也不是与另一个 LLM 的对抗测试。

三场对局均使用常规的机器人初始状态、零初始弹量、常规经济以及完整的 **420 秒**裁判系统时长。内部的空场景规格没有覆盖任何机器人属性。没有注入初始弹量、HP、金币、位置或复活状态。LLM 指令从未重置模拟器。每场比赛均通过裁判系统常规的超时计分结束。

## 结果

| 种子 | 对手配置 | 胜方 | 红 / 蓝攻击伤害 | 红 / 蓝最终基地 HP | 规划器调用次数 | 推理延迟中位数 / p95 |
| --- | --- | --- | --- | --- | --- | --- |
| 9,000,000 | siege | 红方 | 3,000 / 295 | 10,000 / 8,000 | 92 | 1.47 / 2.04 s |
| 9,000,001 | raid | 蓝方 | 100 / 2,280 | 9,020 / 10,000 | 72 | 1.44 / 1.93 s |
| 9,000,002 | hunt | 蓝方 | 100 / 4,160 | 7,080 / 10,000 | 79 | 1.53 / 2.19 s |

**1 胜 2 负。** 三场原生 v4 回放均确定性地验证了各 **8,400 tick**，以及与记录一致的胜方/摘要。实际的 10 Hz 学习执行只控制红方 3 号槽位；对手脚本只接收蓝方自身的合法观测。评估使用默认的墙钟/模拟速度 1。包括启动/调度在内，比赛耗时约 422 秒；包括保存和确定性回放验证在内，整个任务耗时 456 秒。整批对局中共错过十次墙钟截止时间；没有跳过或虚构任何模拟 tick。

共有 **243 次实际 API 请求**、**229 次有效决策**，以及 **14 次格式错误的坐标工具调用**被校验拒绝。没有用任何提供方认证/网络回退来替代。有效决策的总体延迟中位数为 **1.47 s**，p95 为 **2.09 s**。每次有效推理都在模拟时间推进之后才完成；日志显示这些请求期间共有 7,190 个重叠的物理 tick（按 actor/请求累加，而非去重后的对局 tick）。

宿主接受了 105 个新目标、123 次显式继续，并保留了一个语义相同的运行中目标。新接受的技能包括 66 次补给、31 次导航和 8 次建筑攻击指令。其中一些随即被机器人可用性/低 HP 检查拒绝，并以失败目标结束；指令被接受并不等于技能完成。失利对局中的频繁重试是一个弱点，而不是有用的策略多样性的证据。三场评估对局中原生 `invalid_action` 事件为零。

本批次中模型没有选择 `defend_region`、`engage_target`、`pursue_target` 或 `patrol`。接口暴露了这些技能并测试了它们的契约，但本批次**不能**证明真实 LLM 在这些选择上的战术表现。由于红方没有部署友方，护送不可用；由于所选的 2027 地图缺少专用地形，飞坡不可用。早期的局部 RL 课程结果是独立的证据。

## 失败之处

在 siege 对局中，机器人完成补给、穿越场地、攻击敌方前哨站，随后对其基地造成伤害。之后它耗尽了弹药，并在受阻的导航/低 HP 停止上花费了大量时间。对该配置取胜并不能证明其具备稳健的长时程对局能力。

在 raid 对局中，机器人反复经历被击毁/复活的循环。许多撤退导航尝试因现有的低 HP 阈值而立即停止，补给路线也被阻塞。局部导航/补给课程没有充分覆盖受敌方压制时的撤退，以及从这些位置的恢复。

在 hunt 对局中，机器人在约 **63 s** 时翻倒，在 420 个逐秒快照中有 358 个低于直立阈值。当前执行器正确地停止了机器人不可用时的动作。其技能库没有自扶正/救援选项，常规复活也无法修复这种物理状态。尽管处于这种状况，LLM 仍反复请求补给；它需要更好的不可用状态监督，以及具备恢复能力的 RL 课程。评估中没有为了救援它而修改模拟器。

这 14 次格式错误的坐标调用在替换有效的当前目标之前就被拦截。它们的请求上下文、校验错误以及后续决策均被保留。提供方侧的 schema 强制约束或标量坐标形式的工具表示可以减少这类失败；此版本使用稳定的 Chat Completions 端点加宿主校验。

这些结果验证了“真实 API → 战术工具 → 冻结 RL → 裁判系统/回放”这条管线。它们表明**全场对局可靠性仍然有限**，尤其是在防守选择、受压制时的撤退和物理恢复方面。运行器的 `healthy_control` 字段表示集成/连续性已完成且 API 指令有效，并不代表机器人健康、战术质量或胜利。

## 复现与检查

```bash
uv run arena-rl llm-matches --policies checkpoints/tactics \
  --matches 3 --seed 9000000 --max-calls 150 \
  --output runs/deepseek-full-new
```

请使用新的输出目录。即使模拟器种子相同，API 采样和墙钟到达时间也会使新的运行不具确定性。原生回放验证是确定性的，且不调用 API。检查点保持冻结；本次评估中没有进行任何 RL 训练或权重更新。

仓库包含[报告、完整的决策/遥测日志、指令伴随文件和 SHA256 清单](../../evaluations/deepseek-v4.1-flash-2026-10-18)。完整的原生回放（每个约 190 MiB）保存在本地 `runs/deepseek-v4.1-flash-full/` 下，未纳入 Git，以免每次克隆都增加数百 MiB。它们的哈希和已验证的摘要记录在已提交的报告/清单中。源码哈希快照记录了被评估的控制器；此后仅为 0.4.0 修改了包版本元数据。

全部 **78 项本地测试**均已通过，涵盖纯协议/提供方测试以及模拟器集成/回归测试。新的全时长测试使用明确标注的假规划器，认证失败测试则检查部分运行不能被报告为完整对局。这些测试不计入上述真实 API 性能统计。自动 CI 运行纯契约/本地 mock 提供方检查；完整的模拟器集成仍需要 Arena-1 对应的、尚未发布的本地前置依赖。

Arena-RL 在记录本文时为私有仓库；自 2026-10-19 起已公开。本工作未提交、推送或发布 Arena-1。
